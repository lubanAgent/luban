# 快速接入

从一个“通话文本 → Agent 摘要 → 接口返回”的例子开始。先用模拟模型跑通，再替换自己的业务函数和网关。

## 1. 先跑完整示例

在仓库根目录执行：

```sh
cd sdk
go run ./examples/call-summary
```

输出最后一行为：

```text
输出：{"summary":"客户想了解周末课程，顾问将于明天下午发送课程安排并电话确认。"}
```

默认执行一次内存 HTTP 请求，经过真实 Gin 路由和 Luban Handler；不监听端口，不访问外部模型或数据库。模拟模型忽略输入，返回固定文本。首次下载 Go 依赖可能需要联网。

| 文件 | 看什么 |
| --- | --- |
| [agent.json](../sdk/examples/call-summary/agent.json) | 一份完整 Agent 配置，最外层直接是 `callSummary`。 |
| [main.go](../sdk/examples/call-summary/main.go) | 配置读取、New/Register、路由绑定、业务节点和响应。 |
| [model.go](../sdk/examples/call-summary/model.go) | 可运行的模拟模型；接真实网关时替换这里。 |

需要用 curl 体验时，在 `sdk` 目录启动示例自己的本机服务：

```sh
go run ./examples/call-summary -listen 127.0.0.1:8080
```

另一个终端发送：

```sh
curl -X POST http://127.0.0.1:8080/summary \
  -H 'Content-Type: application/json' \
  -d '{"text":"客户咨询周末课程，顾问明天下午跟进。"}'
```

这里仍是固定模拟回复。接到已有项目时，直接绑定原有 Gin 路由即可，无须新增监听服务。

## 2. 启动时：读取配置，创建并注册

以下是示例里的完整初始化函数；其依赖的业务函数和模拟模型都在上面的源文件中。读取 JSON 的位置由业务决定，SDK 不扫描文件：

```go
func newRuntime(configPath string) (*luban.Runtime, error) {
    raw, err := os.ReadFile(configPath)
    if err != nil {
        return nil, fmt.Errorf("读取配置：%w", err)
    }
    var config luban.Config
    if err := json.Unmarshal(raw, &config); err != nil {
        return nil, fmt.Errorf("解析配置：%w", err)
    }

    rt, err := luban.New(luban.Options{
        Config: config,
        Models: map[string]luban.ModelInvoker{"demo": demoModel{}},
    })
    if err != nil {
        return nil, err
    }
    if err := rt.Register(map[string]any{
        "PrepareCall": PrepareCall,
        "BuildResult": BuildResult,
    }, nil, nil); err != nil {
        return nil, err
    }
    return rt, nil
}
```

`Register(funcs, tools, skills)` 在启动时调用一次；未用的 Tool、Skill 传 `nil`。成功后，入口共享这个 Runtime。配置的 `func` 按函数表 key 查找，`modelName` 按 `Models` 的 key 查找；引用不存在时执行报错。

## 3. 执行时：首函数解析输入，后一个函数接收结果

本例的传值过程：

| 位置 | 收到什么 | 交给后面什么 |
| --- | --- | --- |
| `PrepareCall(ctx)` | 从 Gin Context 解析请求中的 `text` | `luban.Request`，包含本次通话消息 |
| Agent 节点 | 配置里的 `systemPrompt` + 本次 `Request.Messages` | 模型最终正文 `string` |
| `BuildResult(ctx, summary)` | 上一步的 `string` | 业务结构体 `CallSummary` |
| `render(ctx, output, err)` | 整次执行的结果或错误 | 业务定义的 HTTP 响应 |

这里的 `CallSummary` 是 **BuildResult 组装的接口结构体**。如果希望模型直接提交结构体，应在准备函数返回的 Request 中声明 `Output: luban.Output[YourResult]()`，下一个业务函数就接收 `YourResult`；该方式要求模型调用器支持 Tool Calling。

业务函数的约定：

- 第一个参数必须是 `*gin.Context`，之后最多一个业务输入；最多一个业务输出，末尾可选标准 `error`。
- 相邻节点按 Go 类型可赋值关系传值，不自动解析 JSON 字符串，也不自动转换结构体、指针或数字。
- 一个节点没有业务输出时，不透传更早节点的值。最后执行的节点无输出，成功出口补空 `map[string]any`。
- `systemPrompt` 是配置中的固定指令；动态文本、图片、视频、音频放在 `Request.Messages`。媒体是否可用取决于模型和网关。

## 4. 绑定已有 HTTP、MQ 或 Cron 入口

HTTP 示例使用以下 import：

```go
lubanhttp "github.com/lubanAgent/luban/sdk/entrypoint/http"
```

在项目已有路由注册处使用初始化好的 `rt`：

```go
router.POST("/summary", lubanhttp.Handler(rt, "callSummary", render))
```

`render` 是业务响应函数，签名为 `func(*gin.Context, any, error)`。本例用 Gin JSON 响应，并统一将执行错误返回为 HTTP 500；接入时沿用自己项目的错误码与响应规范。

| 入口 | SDK 提供什么 | 首业务节点怎样接收输入 | 业务继续负责什么 |
| --- | --- | --- | --- |
| HTTP | `lubanhttp.Handler(rt, appKey, render)` | 从 `ctx` 解析 HTTP 请求，SDK 的初始业务输入为 nil | 路由、中间件、响应格式 |
| MQ | `lubanmq.Handler[Message](rt, appKey)` | `func(ctx *gin.Context, msg Message) ...` | 消费框架、ACK、重试、业务收尾 |
| Cron | `lubancron.Job[Item](rt, appKey, loader)` | `func(ctx *gin.Context, item Item) ...` | 调度器、加载任务项、任务记录 |

MQ、Cron 的包路径分别为 `github.com/lubanAgent/luban/sdk/entrypoint/mq`、`github.com/lubanAgent/luban/sdk/entrypoint/cron`。表中的 `Message`、`Item` 是业务自己的类型。`loader` 的签名为 `func(*gin.Context, ...string) ([]Item, error)`；空列表正常结束，非空列表逐项执行，一项失败后继续处理其余项，最终汇总错误。

不同入口的首函数按输入形式解析参数；可以分别配置首节点，复用后面的业务处理。**上面的 PrepareCall 读取 HTTP JSON，不能直接作为 MQ 消息解析函数。**

这些适配器内部同步执行 `Run`，业务节点无需手动调用。需要自行控制入口时，也可以直接使用 `rt.Run(ctx, appKey, input)`。

## 5. 换成真实模型

保留配置与注册方式，将 `Models["demo"]` 中的模拟对象替换为自己的 `luban.ModelInvoker`。也可以修改 key，同时修改配置中的 `modelName`。

| 接口内容 | 模型调用器需要处理什么 |
| --- | --- |
| `Name() string` | 返回调用器名称；配置的查找关系仍以 `Models` 的 key 为准。 |
| `Invoke(ctx, req)` 的请求 | 把 `req.Messages`、`req.Tools`、可选 `req.Temperature` 映射到网关协议。 |
| 返回的 `ModelResponse` | 保留模型正文、ToolCalls 及调用 ID、FinishReason；有真实用量时填写 Usage。 |
| 请求过程 | 使用业务已有 HTTP 客户端，负责鉴权、超时、重试。 |

**每次 Invoke 只做一轮模型请求。** 将模型提出的工具调用交回 SDK，Tool 执行、工具结果回传、后续模型调用由框架组织。Tool、Skill、子 Agent 移交和 `Output[T]()` 都需要网关正确传递工具定义、工具调用与结果关系。只适配文本正文的调用器不能据此宣称支持这些能力。

## 6. 按需使用其他能力

| 想做什么 | 写法或规则 | 继续看 |
| --- | --- | --- |
| 模型直接交付结构体 | 准备函数声明 `Request.Output = luban.Output[T]()`；下游接收 T | [Request/Output](../sdk/request.go) |
| 提供业务 Tool | 实现 `Name/Description/Input/Invoke`，Register 后在 `tools` 中列出名称 | [Tool 接口](../sdk/tool.go) |
| 给 Agent 提供 Skill | 注册 `luban.Skill{Name, Description, Content}`，在 `skills` 中引用；动态正文可由 SkillBackend 提供 | [Skill 接口](../sdk/skill.go) |
| 父选择子 Agent | 配置 `subAgents`，子独立设置模型、提示词、Tool 和 Skill；父正常未移交时下游收到 nil | [配置类型](../sdk/config.go)、[行为测试](../sdk/agent_test.go) |
| 同批处理多条输入 | 返回 Batch，按下标收集 BatchResult；空批次返回 `ErrEmptyBatch` | [Batch 类型](../sdk/batch.go)、[行为测试](../sdk/batch_test.go) |
| 跨非相邻节点或 Tool 共享数据 | `luban.Set(ctx, key, value)` / `luban.Get(ctx, key)`；普通 Tool 可读写，Batch 只读 | [数据接口](../sdk/data.go)、下节示例 |
| 正常提前结束 flow | 业务函数调用 `luban.Stop(ctx)` 后显式 return；正常返回该节点输出。Tool 调用 Stop 会报错 | [Stop/Run](../sdk/run.go) |
| 从某个业务节点开始 | `rt.RunFrom(ctx, appKey, startFunc, input)`；指定函数在 flow 中必须唯一，不恢复旧 Run 状态 | [RunFrom](../sdk/run.go) |
| 在回调中判断当前 Agent | `luban.CurrentAgent(ctx)`；获取本次选择结果用 `luban.SelectedSubAgent(ctx)`，都应检查 bool | [AgentScope](../sdk/skill.go) |
| 查看执行记录 | 注入 TraceWriter；用 `luban.RunID(ctx)` 关联事件 | [Trace 接口](../sdk/trace.go)、[查看页](../sdk/trace-viewer/README.md) |

Tool 的 Input 返回参数类型样本；Invoke 接收 SDK 解析的值并返回结果。Schema 推导和参数解析沿用 Eino，领域校验、外部副作用与幂等由业务处理。每个 Agent 的 `maxLoopCount` 默认 5，限制模型生成轮数；父子分别计数，不包含网关内部重试。

## 7. 在多个节点与 Tool 间共享数据

相邻节点的业务输入仍通过 return 传递。如果一个可信 ID 要跨过模型节点，或 Tool 查到的数据还要给后面的函数使用，可以放进本次 Run 的共享容器：

```text
准备函数：Set("callID", 42)
    ↓
Agent → Tool：Get("callID")，必要时 Set("customer", 查询结果)
    ↓
后续函数：Get("callID") / Get("customer")
    ↓
Run 返回：容器清理
```

例如，下面两个业务函数可放在 Agent 节点前后；上方首页示例继续保持最小写法，无需共享数据就不用增加它。

```go
func PrepareCallByID(ctx *gin.Context, callID int64) (luban.Request, error) {
    if err := luban.Set(ctx, "callID", callID); err != nil {
        return luban.Request{}, err
    }
    return luban.Request{Messages: []luban.Message{{
        Role: luban.RoleUser,
        Content: []luban.Part{{
            Type: luban.PartText,
            Text: "请总结本次通话。", // 实际项目在这里填入取得的通话文本。
        }},
    }}}, nil
}

func BuildSummaryByID(ctx *gin.Context, summary string) (map[string]any, error) {
    value, found := luban.Get(ctx, "callID")
    callID, typed := value.(int64)
    if !found || !typed {
        return nil, fmt.Errorf("缺少正确类型的 callID")
    }
    return map[string]any{"callID": callID, "summary": summary}, nil
}
```

使用时导入标准库 `fmt`、Gin 和 Luban；将两个函数显式 Register，并在配置中引用。首节点接收 int64 输入，适合由 Run/MQ/Cron 传入；HTTP 首节点需从请求解析 ID。

| 规则 | 含义 |
| --- | --- |
| 不增加入口参数 | Run/RunFrom 自动建立容器，每次执行独立；不是跨请求存储。 |
| Get 检查 bool | 未写入返回 nil、false；写入 nil 后返回 nil、true。 |
| Set 检查 error | 无有效 Run、Run 已结束或 Batch 内写入都会报错。 |
| 普通 Tool 可共享 | Gin 副本仍能访问同一容器；原生 `ctx.Set` 只写当前副本，不回写。 |
| Batch 只读 | 每项读批次开始时的公共快照，通过 BatchResult 交付结果；汇总函数可继续读写原容器。 |
| 有锁仍有边界 | Set/Get 本身可并发；取出的 map/slice/指针、Get→修改→Set 的组合操作需业务自行同步。同 key 并发写取最后写入的值。 |
| 数据何时消失 | 正常、Stop、error、panic 都会清理；保存的 Gin 副本也不能继续存取。 |

容器内容不会自动加入 Prompt。Batch 快照只复制键值映射，业务仍须保证其中可变对象只读。

## 8. Stop：由业务节点决定是否结束流程

```go
func CheckQuota(ctx *gin.Context, remaining int) (int, error) {
    if remaining <= 0 {
        luban.Stop(ctx)
        return 0, nil // 显式 return 后结束 flow，Run 返回 0、nil。
    }
    return remaining, nil
}
```

Tool 如果需要表达“任务应结束”，先返回业务结果，让后续业务节点判断并调用 Stop。Tool 内调用 Stop 会成为带工具名的执行错误，不能通过自行 recover 变成正常停止；Batch 中记录在对应项的 Err。Stop 不撤销副作用，也不能覆盖业务错误或请求取消。

## 9. 运行约定

- `Run` 同步完成，正常返回最后实际执行节点的输出；错误返回 `nil, error`，不交付部分结果。没有声明 Output 时，模型最终正文原样返回为 string。
- HTTP 的取消源来自 Request.Context；在途模型请求是否中止，取决于业务调用器是否传递该取消信号。MQ/Cron 没有 Request 时不会自动获得任务取消源，业务配置请求超时和重试。
- 同一次 Run 的顺序业务函数使用同一个 Gin Context；Tool/Batch 使用副本。需要跨副本共享时显式使用 `luban.Set/Get`，规则见第 7 节。SDK 不补齐公司 Gin 扩展字段。
- 当前没有实时流式输出、配置分支/回跳或跨请求恢复；外层 flow 顺序执行，Agent 内仍有模型与工具循环。配置由业务启动时提供，缓存到期不代表会热更新最初传入的变量。

TraceWriter 需要支持并发调用，可将完整 TraceEvent 作为单行 JSON 写入现有日志；用 runId 筛选后导入本地查看页。完整事件可能包含消息、Tool 参数和 Skill 正文，日志访问权限沿业务管理。
