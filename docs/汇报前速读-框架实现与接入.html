一条消息走完鲁班 Agent：当前实现与业务接入

用 Wecombot 的 trustee Agent 贯穿启动装配、MQ 接入、顺序执行、模型工具循环、质检和收尾。

事实阶梯

先说人话，再把事实讲到底。

可以把 Runtime 想成接线台：业务把方法和网关插上，配置告诉它按什么顺序接线。这个说法只是帮助记忆。

每次 Run 根据 appKey 取得配置快照，临时编译 Eino Chain；函数经反射调用，Agent 节点构建 ChatModelAgent，模型请求委托业务 ModelInvoker。

这是当前代码的能力，不等于所有业务自动零代码接入。Wecombot 的前置状态、候选动作、质检与真正发送仍由业务实现；RunFrom 是新的指定节点入口，不保存跨 Run 状态。

术语表

值得记住的词

appKey
一次 Run 选择哪套 Agent 配置的键；示例是 trustee。
Request
业务函数交给模型节点的动态消息与可选结构化输出声明。
ModelInvoker
业务实现的模型调用接口；SDK 用它访问原有网关。
OutputTool
声明 Output[T]() 时 SDK 给模型注册的内部结果提交工具。
Stop
业务函数请求本次 flow 在该节点正常结束，函数还需自行返回。
TraceWriter
业务可选实现的事件写入接口，当前 wecombot 写入日志。

复述检验

现在能用自己的话讲清楚吗？

配置写了 prepareTrustee，SDK 怎么找到实际 Go 函数？

启动时 worker.Functions() 建立名字到方法的 map，rt.Register 登记；Run 按配置名字找到并通过签名适配调用。

子 Agent 调用 send_wx_msg 就已经发给用户了吗？

没有。当前 Wecombot 的 Tool 先记录候选动作，后续 prepareQuality、approveQuality 检查通过，executeApprovedActions 才执行。

一个 consume-events 消息会调用几次 Run？

目前入口 Handler 同步调用一次 rt.Run(ctx, "trustee", message)；父选择子与质检都在这套 flow 内。
